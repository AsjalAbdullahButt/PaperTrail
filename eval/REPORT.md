# PaperTrail — Evidence-Grounded Research-Paper Question Answering over an NLP Corpus using Hybrid RAG

NLP course project · category: **RAG Bot for a Niche Domain** · niche domain: **research papers on NLP techniques** (transformers, embeddings, dense / late-interaction retrieval, retrieval-augmented generation and its evaluation).

> **How to read the numbers.** Every table in this report is generated by `eval/run_eval.py` / `eval/analysis.py` and injected by `eval/render_docs.py`; the plain-text companion `Report.txt` receives the same tables from the same files, so the two documents cannot disagree. The whole evaluation runs on free resources: two local Hugging Face embedding models, local cross-encoder / NLI models, and the Groq free tier for generation and judging. **Retrieval metrics cover every configuration.** Answer-quality metrics (correctness, faithfulness, relevance, citation accuracy, unanswerable handling) cover only the configurations listed in §5.1, because Groq's free tier allows roughly 200,000 tokens per model per day; results accumulate across runs and any table that has not been generated says so explicitly. The harness refuses to run offline (`--require-online`).

## 1. Problem statement and domain

Researchers and students constantly ask questions that are answered inside a small, specialised body of papers: *what negative-sampling scheme does DPR use? how does ColBERT score a passage? how do REALM and RAG differ in updating their retriever?* A general-purpose chatbot answers these from parametric memory and may fabricate details or cite nothing. PaperTrail instead answers **only from retrieved passages**, cites them inline as `[1] [2]`, checks each answer sentence against the evidence, and says so when the corpus does not contain the answer.

This project builds and **measures** that behaviour on a niche, real corpus: 14 NLP research papers on exactly the techniques PaperTrail itself is built from. The NLP problems exercised are document preprocessing and chunking, text embeddings, sparse + dense + fused retrieval, **cross-encoder re-ranking**, **query expansion (HyDE)**, grounded generation, **natural-language-inference (NLI) fact-checking of the generated answer**, **abstention calibration**, and evaluation of RAG systems (retrieval metrics, LLM-as-judge and its validation, citation accuracy).

No model is trained or fine-tuned; everything uses pretrained models (embeddings `all-MiniLM-L6-v2` and `bge-small-en-v1.5`, cross-encoder `ms-marco-MiniLM-L-6-v2`, NLI `nli-deberta-v3-small`, and Groq-hosted LLMs), in line with the course guidelines.

Preprocessing (`eval/build_dataset.py`): PyMuPDF page text is NFKC-normalised (ligatures), hard line-wraps are re-joined into paragraphs, line-end hyphenation is undone, page numbers are dropped, numbered section headings (`3.2 Dense Retrieval`) are detected and written as markdown headings, a `<!-- page: N -->` marker keeps page provenance, and the References section of each paper is removed. Heading detection is heuristic (two-column PDFs occasionally yield a spurious heading), so section-level hit is a secondary metric.

## 3. System and pipeline

`eval/pipeline.py` exposes each stage as a callable function and reuses production code. **The same stages run in the web application** (§9), each as an opt-in switch that defaults to off, so the evaluation measures exactly what a user can turn on.

| Stage | Implementation (production module) | Web-app switch |
|---|---|---|
| load | markdown corpus listed in `manifest.csv` | — |
| chunk | `ingestion.chunk_blocks` (character, 800 chars / 150 overlap) and `chunk_blocks_semantic` (sentence-boundary; ≈3,000 chars by default or capped at ≈800) with page + section provenance | `CHUNKING_STRATEGY` |
| contextual headers *(advanced)* | `ingestion.contextualize_chunk`: embed `"<title> \| <section>\n<chunk>"`; display/BM25 text unchanged | `CONTEXTUAL_CHUNK_HEADERS` |
| importance | `services.importance.score_chunks` per document, as at upload | always |
| embed | `llm.embed_texts` with `embedding_provider` = `hf` (MiniLM or BGE-small, 384-d, L2-normalised); `openai` remains the production default | `EMBEDDING_PROVIDER` |
| query expansion *(advanced)* | `services.query_expansion.hyde_passage`: an LLM writes a hypothetical answer passage; dense search embeds it, BM25 sees question + passage | per-query "HyDE" |
| retrieve (dense) | `similarity.top_k_by_similarity` (cosine) | — |
| retrieve (hybrid) | candidates = top 100 by cosine ∪ top 100 by `BM25Index`; each score min-max normalised; fused `0.6·dense + 0.4·sparse`; × `(1 + 0.2·importance)` | default |
| re-rank *(advanced)* | `services.reranker.rerank`: cross-encoder `ms-marco-MiniLM-L-6-v2` re-scores the top-20 hybrid candidates, top 5 kept | per-query "Re-rank" |
| abstain *(advanced)* | `services.abstention`: skip generation when the top passage's signal (dense cosine, or re-ranker probability) is below a calibrated threshold | per-query "Abstain if unsure" |
| generate | `llm.generate_answer(question, top-5 chunks, mode="rag")`: answer only from the context, cite `[n]`, say so if it is not there | always |
| ground *(advanced)* | `services.nli_guard`: each answer sentence is tested for **entailment** by `nli-deberta-v3-small` against the best-overlapping passage windows | per-query "NLI grounding" |
| ground (default) | `services.hallucination_guard`: lexical key-term overlap | default |

**Deviation (documented).** `services.retriever.hybrid_retrieve` is bound to a database session and per-user caches, so the eval's `retrieve_hybrid` re-implements its *scoring* on in-memory arrays; fusion weights, importance multiplier and min-max function are **imported from the production module**. The only functional difference is that dense candidates come from exact cosine rather than production's approximate index. The re-ranking, HyDE, NLI and abstention services are imported and called directly (no re-implementation). LangChain/LlamaIndex are not used (optional in the guidelines).

**Hallucination guards.** The default guard is a **lexical, heuristic** check: it flags a sentence when fewer than three of its key terms occur in any one retrieved chunk. It can pass a fluent but wrong claim that reuses source vocabulary and flag a correct paraphrase; it is not proof of factual grounding. The NLI guard is the semantic alternative; §7.2 measures both against an LLM judge.

## 4. Evaluation methodology

### Test set

<!-- BEGIN:testset_stats -->
46 questions: 27 factual, 11 multi-hop (evidence in two papers), 8 unanswerable (answer deliberately absent from the corpus).
<!-- END:testset_stats -->

All questions were written from the papers themselves (not generated by the model being evaluated). Every answerable question carries **verbatim evidence quotes** (one per supporting paper) plus optional `any_of` phrases for facts a paper states in several places; `eval/verify_testset.py` checks mechanically that each quote occurs in the corpus, records its page and section, and, for unanswerable questions, checks that the key terms the question depends on occur **nowhere** in the corpus. Multi-hop questions require facts from two papers. The test set was drafted by the authors with AI assistance from the paper text and verified mechanically; a human read-through of the wording and reference answers is still recommended before grading.

### Experiment grid

A configuration is `chunker__retrieval__embedder`. The **core grid** has ten configurations: `character` × {dense, hybrid} × {hf, bge}, `sentence800` × {dense, hybrid} × {hf, bge}, and `sentence` × {dense, hybrid} × {bge}. The **advanced arms** (`--advanced`) each change exactly one stage of a core hybrid configuration, so every comparison is controlled: `…__hybrid_rerank__…` (+ cross-encoder), `…_ctx__hybrid__…` (+ contextual headers), `…__hybrid_hyde__bge` (+ HyDE). `hf` = all-MiniLM-L6-v2 (256-word-piece window), `bge` = BGE-small (512). MiniLM is never paired with the ≈3,000-character chunker; BGE is, but truncates it to roughly its first 2,000 characters (stated in the uncontrolled chunking comparison).

### Metrics

Retrieval (answerable questions): **Doc Recall@5**, **Evidence Recall@5** (a retrieved chunk contains the supporting quote or an `any_of` phrase), **Evidence MRR**, **section hit**. Generation: **correctness**, **faithfulness**, **relevance** (LLM-as-judge, 1–5, against the reference answer and retrieved context; blank `manual_score` column for hand grading), **citation accuracy** and coverage, **unanswerable handling** (abstention on unanswerable questions), and the guard's flagged-sentence rate. Beyond accuracy: **AUROC** of retrieval-confidence signals for abstention, agreement of grounding methods with the judge, inter-judge agreement, and a **failure taxonomy**. Intervals are bootstrap 95% CIs over questions; comparisons are paired bootstraps on per-question differences (`*` marks intervals that exclude 0).

**Findings (answer quality; four scored configurations).** Quality tracks the retrieval configuration: one of the weakest retrievers in the grid (`character__dense__hf`) has the lowest correctness and faithfulness, and the three hybrid configurations are all higher. Moving from dense to hybrid retrieval on that configuration raised judged correctness by about +0.6 (interval just includes 0) and judged faithfulness by about +0.7 (interval excludes 0, see §6.1) — evidence that retrieval quality propagates to the generated answer. **Cross-encoder re-ranking, in contrast, did not change answer quality** (§6.4: Δ correctness ≈ 0, Δ faithfulness slightly negative, both intervals include 0) even though it raised passage-level retrieval metrics: with five passages in the prompt the generator was already getting enough evidence, so better *ordering* bought little, and the re-ranker's loss of document coverage on multi-hop questions offsets its precision gain. Citation accuracy stays below 50% in every scored configuration — most `[n]` markers point at a passage that does not contain the gold quote even when the answer is right — the largest remaining weakness. The HyDE configuration is retrieval-scored only: its answers could not be generated before the free-tier token limit was reached.

### 6.7 Findings (retrieval)

These statements describe the retrieval results above; with ≈38 answerable questions most single differences are within noise, so they cite the intervals.

* **Hybrid retrieval never hurt and usually helped** document recall (≥ 0 in all five dense→hybrid pairs; two intervals exclude 0). Evidence-recall gains are positive-leaning but mostly inside their intervals. Hybrid also raised multi-hop Doc Recall in every pair.
* **BGE-small beat MiniLM on most pairs but not all**; with hybrid retrieval on 800-character sentence chunks the two have essentially the same Evidence Recall@5, i.e. BM25 fusion appears to narrow the gap between a weaker and a stronger embedder (one pair, so only suggestive).
* **The chunking effect is mostly chunk size, not boundary alignment**: the ≈3,000-character chunker wins on Evidence Recall@5 in the uncontrolled comparison, but with size held constant the differences shrink to a few points with intervals that include 0. Larger chunks also cost section attribution.
* **Re-ranking raises passage precision but can cost coverage.** It lifts Evidence Recall@5 and MRR in all four pairs (significantly for `character`/MiniLM) and raises section hit sharply, because the cross-encoder reads question and passage together. Doc Recall@5 is flat or lower — significantly lower for `sentence800`/BGE — and multi-hop Doc Recall falls (e.g. 86% → 64% there). A plausible reading is that the cross-encoder scores each passage independently against the whole question, so five passages from the single best paper can crowd out the second paper a multi-hop question needs; the trade-off is real and is why re-ranking is a per-query switch rather than a default.
* **Contextual chunk headers gave no reliable benefit**: Evidence Recall@5 moves by 0 to +6.6 points (one borderline interval) while Doc Recall@5 is slightly lower in all four pairs. In papers the chunk text already names its subject, so prepending the title adds little; this is a null result worth reporting.
* **HyDE gave the largest retrieval gain** (≈ +25 points of Evidence Recall@5, intervals exclude 0; MRR 0.48 → 0.66 for `character`/BGE) — **with a strong caveat**: these are famous papers that the LLM has largely memorised, so its hypothetical passages sometimes restate the exact gold fact (e.g. for the multi-head-attention question it writes `h = 8`, `d_k = d_v = 64`). On documents the LLM has never seen the benefit would be smaller. The experiment demonstrates the mechanism, not the size of the effect on a private collection.
* **Doc Recall@5 overstates retrieval quality**: it sits far above Evidence Recall@5 in every configuration — the right paper is usually found, the right passage often is not.

### 7.1 Abstention: when should the system say "I don't know"?

A system that always answers will hallucinate on questions the corpus cannot answer. The 8 unanswerable questions are used to test whether the best passage's retrieval score predicts that a question is unanswerable.

<!-- BEGIN:abstention -->

Its advantages are practical: it costs no LLM call (the generator is skipped entirely), it is explicit and tunable, and it does not depend on the LLM's mood. Only 8 unanswerable questions exist, so intervals are wide and thresholds must be re-calibrated for any other embedding model or corpus; the leave-one-out accuracy is the honest estimate.

### 7.2 Is NLI a better grounding check than the lexical heuristic?

<!-- BEGIN:nli_grounding -->
Per answerable, non-abstained answer: fraction of sentences each method flags as unsupported, compared with the LLM judge's faithfulness score (1-5). A good grounding check has a strongly **negative** rank correlation with faithfulness (more flagged = less faithful). *AUROC* = how well "fraction supported" separates answers the judge rated faithful (>= 4) from the rest. The judge is itself an imperfect reference.

| Method | n answers | Mean flagged-sentence rate | Spearman ρ vs judge faithfulness | AUROC for judge-faithful (≥4) |
|---|---|---|---|---|
| Lexical guard (production heuristic) | 135 | 10% | -0.24 | 0.71 |
| NLI entailment, binary (flagged if P(entail) < 0.5) | 135 | 56% | -0.03 | 0.46 |
| NLI mean entailment probability (continuous; ρ expected **positive**) | 135 | 57% (1 − mean P) | +0.07 | 0.50 |

Judge-faithful answers (≥4): 124/135 — with few low-faithfulness answers the AUROC is noisy.
<!-- END:nli_grounding -->

**Finding (a negative result).** The off-the-shelf small NLI model is **not** a better grounding check here. It flags more than half of all answer sentences as unsupported although the judge rates about 92% of the answers faithful, and its flagged rate or mean entailment probability has essentially no rank correlation with the judge's faithfulness score (ρ ≈ 0, AUROC ≈ 0.5), whereas the lexical heuristic, crude as it is, has a modest but real negative correlation (ρ ≈ −0.24, AUROC ≈ 0.71). A direct probe shows why: `nli-deberta-v3-small` (trained on SNLI/MNLI) gives "the base Transformer uses eight parallel attention heads" only about 1% entailment against the passage "we employ h = 8 parallel attention layers, or heads", because it handles numerals, symbols and technical paraphrase poorly, while it correctly entails a verbatim copy (98%). Hence NLI grounding is shipped as an *experimental, opt-in* switch with an explicit "neutral does not mean wrong" caveat, and the lexical guard stays the default. A larger or scientific-text-tuned NLI model (or per-claim decomposition before entailment) is the obvious next experiment. The judge itself is an imperfect reference, so these correlations are indicative rather than definitive.

## 8. Failure analysis (retrieval)

Worked examples from the Hugging Face-embedding retrieval runs (per-question detail: `results/raw_<config>.csv`; deterministic, so reproducible):

1. **Right paper, wrong passage — `q19` (ColBERT scoring).** With `character__dense__hf` all five retrieved chunks come from the ColBERT paper (Doc Recall 100%), yet none contains the sentence that introduces the MaxSim operator. Document-level recall alone would have reported a perfect retrieval; Evidence Recall exposes the miss. Only `sentence800__dense__hf` retrieves it among the four original HF configurations. **Re-ranking does not fix it** (evidence recall stays 0 in all four re-rank arms), but **HyDE does** (`character__hybrid_hyde__bge` finds it): the hypothetical passage contains the vocabulary ("MaxSim", "late interaction") that the question lacks.
2. **Cross-paper confusion — `q25` (the three RAGAS aspects).** In both character-window configurations four of the five retrieved chunks come from the RAG survey rather than from RAGAS, and the one RAGAS chunk retrieved does not contain the sentence defining the three aspects; `sentence800__dense__hf` retrieves no RAGAS chunk at all. The survey restates RAGAS's triad, so in a corpus where papers cite and re-describe each other, retrieving the *secondary* source is a natural failure, and it matters for citation accuracy. **Re-ranking fixes this case**: all four re-rank arms retrieve the defining sentence, because the cross-encoder reads the question and passage together and prefers the primary source.
3. **Chunk boundaries can decide the outcome — `q21` (BEIR's BM25 finding).** In the two character-window configurations no retrieved chunk contains the abstract sentence stating the finding, whereas both sentence-aligned ≈800-character configurations retrieve a chunk that does. Re-ranking and HyDE also recover it for the character windows.
4. **Multi-hop splits one top-5 between two information needs — `q38` (Contriever's benchmark and BEIR's size).** In all four original HF configurations both papers are retrieved, but neither supporting sentence is among the passages. Multi-hop Doc Recall is lower than single-hop Doc Recall in the retrieval table. Neither re-ranking nor HyDE helps here: evidence recall for this question drops from 0.5 to 0 under both, a concrete instance of the multi-hop cost of re-ranking noted in §6.7.

Answer-level failure analysis is §7.4 (taxonomy) plus the `judge_rationale` column of the scored `raw_<config>.csv` files.

## 9. The web application

Everything above is available to a user of the PaperTrail web app (Next.js + FastAPI), not just to the evaluation scripts. Under the query box a **"NLP pipeline"** bar offers four switches, each defaulting to the server setting and disabled (with the reason) when the server cannot run it:

| UI control | Backend stage | What the user sees |
|---|---|---|
| **Re-rank** | cross-encoder re-ranking of the hybrid top-20 | each source card shows a *Re-rank %* chip; order and relevance meter follow the cross-encoder |
| **HyDE** | LLM-written hypothetical passage used for retrieval | a "HyDE query expansion" badge on the answer |
| **NLI grounding** | entailment check of every answer sentence | a *Claim-by-claim grounding* panel: each sentence with its entailment %, click-through to the supporting source card; "NLI" vs "Lexical" badge |
| **Abstain if unsure** | retrieval-confidence threshold | an amber *"Declined to answer"* banner showing the relevance score; the retrieved passages are still listed |

Every source card also shows the **retrieval inspector** chips — *Dense %, BM25 %, Importance %, Re-rank %* — so the user can see why a passage was retrieved, and **pipeline badges** under the answer record exactly which stages ran (and any fallback, e.g. "Re-ranking skipped: sentence-transformers is not installed"), so an answer can never be mistaken for one produced by a different configuration. The server exposes `GET /api/query/capabilities` for the toggles; `POST /api/query` and `/api/query/stream` accept `options`; responses add `abstained`, `grounding`, `pipeline` and per-source `sparse_score` / `rerank_score` / `rerank_prob`. Server defaults come from `RERANK_ENABLED`, `QUERY_EXPANSION`, `GROUNDING_METHOD`, `ABSTAIN_ENABLED`/`ABSTAIN_THRESHOLD*` and `CONTEXTUAL_CHUNK_HEADERS` (documented in `backend/.env.example`). Backend tests (stubbed models) and frontend tests cover all four paths.

## 10. Limitations

* **Small, curated test set.** 46 questions over 14 papers expose retrieval patterns, but intervals are wide; abstention calibration rests on only 8 unanswerable questions.
* **Partial answer-quality coverage.** Because of the Groq free-tier token limits only some configurations have answer-quality scores (§5.1); comparisons that need generation metrics are reported only where both configurations were scored. The advanced arms were evaluated mainly on retrieval metrics.
* **Judge bias.** Generation (`gpt-oss-120b`) and judging (`gpt-oss-20b`) use different models but share a family and style. §7.3 reports agreement with a second judge from another family; the human column is provided but must be filled by a person.
* **LLM memorisation inflates HyDE** (§6.6); the corpus is famous papers.
* **Evidence matching is textual**: a chunk that paraphrases a fact is not credited, so Evidence Recall is conservative.
* **Section labels are heuristic**; **hybrid retrieval is re-implemented** with exact dense candidates (§3); thresholds are embedding-model specific.
* **Two small embedding models, one corpus domain.** No hosted embedding model (OpenAI) was evaluated.
* **Single-turn evaluation.** Conversation history and the live app's multi-hop and compare modes are outside the measurements.
