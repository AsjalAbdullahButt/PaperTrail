# PaperTrail — Evidence-Grounded Research-Paper Question Answering over an NLP Corpus using Hybrid RAG

NLP course project · category: **RAG Bot for a Niche Domain** · niche domain: **research papers on NLP techniques** (transformers, embeddings, dense / late-interaction retrieval, retrieval-augmented generation and its evaluation).

> **Status of the numbers in this report.** All tables are generated by `eval/run_eval.py` and injected by `eval/render_docs.py`; no number is typed by hand. Retrieval metrics for the Hugging Face-embedding configurations were produced with real embeddings. Metrics that need a working LLM or OpenAI embeddings (answer correctness, faithfulness, relevance, citation accuracy, unanswerable handling, and every OpenAI-embedding configuration) appear as *"Not generated by the last run"* until `python run_eval.py` is run with valid keys in `backend/.env` (see `eval/README.md`). The harness refuses to run those parts offline (`--require-online`).

## 1. Problem statement and domain

Researchers and students constantly ask questions that are answered inside a small, specialised body of papers: *what negative-sampling scheme does DPR use? how does ColBERT score a passage? how do REALM and RAG differ in updating their retriever?* A general-purpose chatbot answers these from parametric memory and may fabricate details or cite nothing. PaperTrail instead answers **only from the retrieved passages**, cites them inline as `[1] [2]`, flags weakly supported sentences, and says so when the corpus does not contain the answer.

This project evaluates that behaviour on a **niche, real corpus: 14 NLP research papers** on exactly the techniques PaperTrail itself is built from (embeddings, hybrid retrieval, RAG, RAG evaluation). The questions asked are the questions an NLP student would ask while studying the field, including cross-paper questions and questions the corpus cannot answer. The NLP problems exercised are: document preprocessing and chunking, text embeddings, sparse + dense + fused retrieval, grounded generation, and evaluation of RAG systems (retrieval metrics, LLM-as-judge, citation accuracy, abstention).

No model is trained or fine-tuned; the project uses pretrained embeddings (OpenAI `text-embedding-3-small`, Hugging Face `all-MiniLM-L6-v2`) and a hosted LLM, in line with the course guidelines.

Preprocessing (`eval/build_dataset.py`): PyMuPDF page text is NFKC-normalised (ligatures), hard line-wraps are re-joined into paragraphs, line-end hyphenation is undone, page numbers are dropped, numbered section headings (`3.2 Dense Retrieval`) are detected and written as markdown headings, a `<!-- page: N -->` marker is kept so chunks carry page provenance, and the References section of each paper is removed. Appendices are kept. Heading detection is heuristic (two-column PDFs occasionally yield a spurious heading such as a table caption), which is why section-level hit is reported only as a secondary metric.

## 3. Pipeline

`eval/pipeline.py` exposes each stage as a callable function and reuses production code:

| Stage | Implementation |
|---|---|
| load | markdown corpus listed in `manifest.csv` |
| chunk | `ingestion.chunk_blocks` (character, 800 chars / 150 overlap) and `ingestion.chunk_blocks_semantic` (sentence-boundary; default ≈3,000 chars, or capped at ≈800 chars) with page + section provenance |
| importance | `services.importance.score_chunks` per document, as at upload time |
| embed | `llm.embed_texts` with `embedding_provider` = `openai` (1536-d) or `hf` (384-d, L2-normalised) |
| retrieve (dense) | `similarity.top_k_by_similarity` (cosine) |
| retrieve (hybrid) | candidates = top 100 by cosine ∪ top 100 by `BM25Index`; cosine and BM25 each min-max normalised over candidates; fused `0.6·dense + 0.4·sparse`; multiplied by `1 + 0.2·importance` |
| generate | `llm.generate_answer(question, top-5 chunks, mode="rag")` — "answer only from the context, cite as [n], say so if it is not there" |

**Deviation (documented).** `services.retriever.hybrid_retrieve` is bound to a database session and per-user caches, so it cannot run standalone. `retrieve_hybrid` re-implements its *scoring* on in-memory arrays; the fusion weights, the importance multiplier and the min-max function are **imported from the production module**, so they cannot drift. The only functional difference is that dense candidates come from exact brute-force cosine rather than production's approximate USearch/KD-tree search. LangChain/LlamaIndex are not used (they are optional in the guidelines; the stage-wise pipeline above serves the same purpose and exercises the real production code).

**Hallucination guard.** `services.hallucination_guard.check_answer` splits an answer into sentences and flags one when fewer than three of its key terms (proper nouns, numbers, longer words) occur in any single retrieved chunk. It is a **lexical, heuristic grounding check**: it can miss a fluent but wrong claim that reuses source vocabulary and can flag a correct paraphrase. It is not proof that an answer is factually grounded; the eval measures how well it tracks an LLM judge (§6).

## 4. Evaluation methodology

### Test set

<!-- BEGIN:testset_stats -->
46 questions: 27 factual, 11 multi-hop (evidence in two papers), 8 unanswerable (answer deliberately absent from the corpus).
<!-- END:testset_stats -->

All questions were written from the papers themselves (not generated by the model being evaluated). Every answerable question carries **verbatim evidence quotes** (one per supporting paper); `eval/verify_testset.py` checks mechanically that each quote occurs in the corpus text, records its page and section, and, for unanswerable questions, checks that the key terms the question depends on occur **nowhere** in the corpus. Multi-hop questions require facts from two different papers (for example, "which retriever does RAG initialise from, and how was that retriever's best model trained?"). Unanswerable questions are plausible in-domain questions whose answer is absent (for example, a vector-database recommendation attributed to the RAGAS paper). The test set was drafted by the authors with AI assistance from the paper text and verified mechanically against the corpus; human review of the question wording and reference answers is still recommended before grading.

### Experiment grid

A configuration is `chunker__retrieval__embedder`. Ten configurations are run: `character` × {dense, hybrid} × {openai, hf}, `sentence` × {dense, hybrid} × {openai}, `sentence800` × {dense, hybrid} × {openai, hf}. The HF model truncates input at 256 word-pieces, so it is never paired with the ≈3,000-character chunker.

### Metrics

Retrieval (answerable questions): **Doc Recall@5**, **Evidence Recall@5** (a retrieved chunk contains the supporting quote, or an `any_of` phrase for facts the paper states in several places), **Evidence MRR**, **section hit**. Generation: **correctness**, **faithfulness**, **relevance** (LLM-as-judge, 1–5, one structured call per answer against the reference answer and the retrieved context; a blank `manual_score` column is provided for hand grading), **citation accuracy** (fraction of cited `[n]` passages that contain gold evidence) and coverage, **unanswerable handling rate** (abstention on unanswerable questions, judge verdict cross-checked against a regex), and the guard's flagged-sentence rate. Intervals are bootstrap 95% CIs over questions; comparisons are paired bootstraps on per-question differences (`*` marks intervals that exclude 0).

Trade-offs beyond accuracy: `text-embedding-3-small` is a hosted per-token service (1536-d, no infrastructure, requires a key and network) whereas `all-MiniLM-L6-v2` is a 22M-parameter local model (384-d, free per call, runs on CPU, no data leaves the machine) with a 256-word-piece input limit that forces ≈800-character chunks. PaperTrail keeps OpenAI as the production default because `llm.py` already isolates the provider and has an offline fallback; the HF path is opt-in (`EMBEDDING_PROVIDER=hf`) and exists so embedding models can be compared on the same questions and retriever.

## 7. Failure analysis

Worked examples from the Hugging Face-embedding retrieval runs (per-question detail: `results/raw_<config>.csv`; these runs are deterministic, so the examples are reproducible):

1. **Right paper, wrong passage — `q19` (ColBERT scoring).** With `character__dense__hf` all five retrieved chunks come from the ColBERT paper (Doc Recall 100%), yet none contains the sentence that introduces the MaxSim operator. Document-level recall alone would have reported a perfect retrieval; Evidence Recall exposes the miss. This is why the report leads with evidence-level metrics. (Only `sentence800__dense__hf` retrieves it; both hybrid configurations miss it too, so this is not simply a dense-vs-hybrid effect.)
2. **Cross-paper confusion — `q25` (the three RAGAS aspects).** In both character-window configurations four of the five retrieved chunks come from the RAG survey rather than from RAGAS, and the one RAGAS chunk retrieved does not contain the sentence defining the three aspects; `sentence800__dense__hf` retrieves no RAGAS chunk at all. The survey restates RAGAS's faithfulness / answer-relevance / context-relevance triad, so in a corpus where papers cite and re-describe each other, retrieving the *secondary* source is a natural failure, and it matters for citation accuracy (an answer can be right yet cite the survey).
3. **Chunk boundaries can decide the outcome — `q21` (BEIR's BM25 finding).** In the two character-window configurations no retrieved chunk contains the abstract sentence stating the finding (two of the five are Contriever chunks), whereas both sentence-aligned ≈800-character configurations retrieve a BEIR chunk that contains it. This is one question; whether boundary alignment helps in aggregate is what the size-controlled ablation (§6.3) tests.
4. **Multi-hop splits one top-5 between two information needs — `q38` (Contriever's benchmark and BEIR's size).** In all four HF configurations both papers are retrieved, but neither the specific BEIR sentence ("18 datasets") nor Contriever's BEIR result is among the retrieved passages. Multi-hop Doc Recall is lower than single-hop Doc Recall in the retrieval table.

Answer-level failure analysis (wrong or unfaithful answers, mis-attributed citations, answers to unanswerable questions) is generated from `raw_<config>.csv` once the LLM run is complete; the lowest-correctness rows are the natural place to look.

## 8. Limitations

* **Small, curated test set.** 46 questions over 14 papers is large enough to expose retrieval patterns but its confidence intervals are wide; differences between configurations are often within noise (the `*` marker shows which are not).
* **Judge bias.** By default the same hosted model generates and judges answers, which tends to favour its own style. The judge is given the reference answer and retrieved context and returns a structured verdict, and abstention is cross-checked with a regex, but a second judge model or a human pass (`manual_score`) would be stronger.
* **Evidence matching is textual.** A retrieved chunk "supports" a question only if it contains the gold quote or one of the listed alternative phrases; a chunk that paraphrases the fact is not credited, so Evidence Recall is a conservative estimate.
* **Section labels are heuristic** (PDF heading detection), so section hit is secondary.
* **Hybrid re-implementation** uses exact rather than approximate dense candidates (§3) — an upper bound on production candidate quality.
* **Two embedding models, one corpus domain.** Conclusions about MiniLM vs OpenAI hold for this corpus and these chunk sizes; MiniLM is further disadvantaged by its 256-token window.
* **The hallucination guard is lexical.** See §3; its agreement with the judge is reported in §6.4.
* **Single-turn only.** Conversation history, multi-hop retrieval mode and follow-up generation (features of the live app) are outside this evaluation.
